# CPU 与系统风扇分别温控

CPU 风扇和系统风扇各自保存一套规则，分别选择温度来源。界面中的“CPU／系统”沿用原厂逻辑通道，两个物理风扇的实际对应和机械调速效果仍需在 NAS 上确认；目标输出不等于实测 RPM。

2026-10-28 对 `db9ce08` 镜像的实机软件验收、采证方式和覆盖边界见 [实机验收记录](fan-acceptance.md)。

## 设置入口

浏览器打开 `http://NAS_IP:18732`，已启用登录口令时先登录。网页中 CPU、系统风扇各有一张配置卡；小屏“控制中心 → 风扇状态”显示两路参考温度、触发来源、输出和保护原因。

网页的“转速模式”按原厂实际能力区分：

| 通道 | 选项 | 行为 |
|---|---|---|
| CPU | 自动 | 退出 CPU 独立接管，恢复原厂自动温控 |
| CPU | 高／中／低 | 独立接管 CPU，固定请求输出 100／75／50%，保留温度保护 |
| CPU | 手动 | 独立接管 CPU，直接编辑温控曲线 |
| 系统 | 自动／低档／中档／高档 | 退出系统独立接管，调用原厂接口设置对应档位；分别对应原厂模式 5／2／3／4 |
| 系统 | 手动 | 独立接管系统风扇，直接编辑温控曲线 |

两路均按“自动／高／中／低／手动”排列。CPU 的高／中／低使用独立固定输出；系统的高／中／低使用原厂档位，不换算为百分比。手动直接显示温控曲线，不再二次选择控制类型。旧 CPU 固定配置恰好等于 50／75／100% 时显示对应档位；其他旧 CPU 固定值和所有旧系统独立固定值明确标为旧配置并保留原值，不自动取整或转换为原厂档位。

温控曲线按所选温度设备的最高温执行三段曲线，可一次勾选多个设备；只编辑低温、高温两个阈值和静音／普通输出，全速固定 100%。低于低温阈值为静音，两个阈值之间（含等于低温、高温）为普通，高于高温阈值为全速。每轮只看当前有效温度，升降温使用相同边界，不保留隐式迟滞；设备缺测或过期时按保护规则处理。固定输出同样保留独立的过热与缺测保护。

小屏五档与网页保持相同的通道语义：系统自动／低／中／高明确设置原厂模式 5／2／3／4；CPU 自动退出该路接管，CPU 低／中／高仍为独立固定输出 50／75／100%；手动使用已保存的温控曲线。原厂档位与独立调速分别检查能力，实际原厂高档不能显示成自动。旧系统独立固定百分比明确标为旧配置，不冒充原厂四档；曲线、阈值和温度设备仍在网页编辑。

网页只有一个“保存”按钮，点击即保存并应用，不再弹出风扇确认框，也不需要先复位。点击保存代表本次应用意图；底层接口仍支持只保存待用规则，并保留鉴权、同源、CSRF 和 `confirmed: true` 校验。应用异步完成；页面显示正在切换时不要把它当成已经生效。关闭浏览器不影响后台执行。原厂档位和独立接管分别检查各自能力；独立接管不可用不妨碍通过验证的原厂系统档位。失败会保留原因，不会伪装已经生效。

已接管通道集合不变、监督进程仍处于 `active`，且原厂系统档位无需变更时，修改固定档或温控曲线会重新读取温度来源，直接提交新目标并等待写入回执，不释放接管、不重启原厂进程、不额外先写一次全速。过热或缺测仍立即覆盖为安全全速。原厂现档只从经过驱动、设备、接口和配置检查的固定文件被动读取；不能用网页缓存证明现档，也不为判断是否需要改档先调用原厂 RPC。

被动确认与可能较慢的原厂 RPM 查询分离，普通后台轮询不会导致重复接管。真正设置原厂档位时单独标记变更过程和版本；读取与设置重叠时不使用该次结果跳过交接。

显式设置不同的系统原厂档位时，同一控制事务先退出独立接管并确认原厂恢复，再设置原厂档位并核对回执，最后按所选通道重新应用手动规则。CPU 手动配置保留，交接期间短暂由原厂自动温控，重新接管先保持安全全速。原厂设档期间不持独立控制租约，避免慢请求造成租约失效，或故障恢复重启执行者时仍发送原厂控制信号。网页分别显示已保存选择与实际原厂档位，未知档位保持未知。

系统仍被实际接管时，即使原厂配置文件已写为自动，也必须完成释放与原厂同步；没有实际交接、原厂现档也相同时仍保持幂等。恢复开始保留安全全速，原厂无注入进程初始化并完成策略同步后，不再追加系统全速写入。该固件用 `/tmp/fan` 记录控制档位，自动逻辑在判断档位需要变化时才重新写硬件；如果初始化写入低档后又被外部直接写成全速，缓存仍为低档，同温区的自动检查不会纠正。重复设置自动也不能充当 PWM 或 RPM 读回。原厂自动使用自己的环境温度来源，不由 Toolbox 的 CPU／硬盘读数推定其应有档位；具体函数和静态证据见[原厂控制链](histor-interfaces.md)。

恢复已有原厂固定档位时，除保留打开字符设备身份与实际写入返回值检查，还通过原厂固定 SET 重申同一当前档位，让原厂同时维护控制缓存；不直接写 `/tmp/fan`，不把自动换算为猜测百分比。该 SET 可能保存相同的原厂配置，不能宣传为只读恢复。每次协议调用前后核对进程、驱动和原厂现档；原厂协议没有原子比较交换，仍存在无法完全消除的跨进程改档窗口。发现原厂新选择时优先保留它，恢复未确认须报告原因，不能用 ACK 代替机械验证。

`POST /api/r1/fan` 保持既有授权、同源、CSRF 和确认校验，配置统一返回、保存为 `schema_version: 2`，通道使用 `low_temp`／`high_temp`。系统通道可选 `vendor_mode: "auto"|"low"|"medium"|"high"`，仅在 `mode: "vendor"` 时由显式应用操作下发；CPU 不接受该字段。旧配置缺少此字段时只释放接管并保留原厂现档，不猜为自动。`fan.official` 经同一控制事务协调，并保留另一路已生效规则，不夹带其待用草稿。原厂档位由厂商持久保存，开机恢复独立控制时不重新下发旧档位覆盖其他原厂应用的选择。

旧 `schema_version: 1` 持久配置与 API 请求仍受支持：先完整校验全部旧字段、15–85°C 整数范围和 `quiet_below < normal_at < full_at`，再把 `normal_at` 映射到 `low_temp`、`full_at` 映射到 `high_temp`，丢弃仅用于旧降温迟滞的 `quiet_below`。这保留原升温的主要温度边界；等于原全速温度时按新规则为普通，超过后才全速。校验失败不会试图猜测或修补配置，v1／v2 字段混用同样拒绝。新响应和之后的保存都只含两个阈值。读取旧数据时分别迁移待用配置与最后成功应用配置，不自动应用草稿、不改原有启动恢复授权，也不因读取而改写数据卷。MCP `set_fan_policy` 接受相同两版输入，沿用相同控制器校验与授权边界。

## 温度和输出

每路可以选一个或多个来源，直接取摄氏度数值最高的一项。例如 CPU=58°C、盘1=39°C、盘2=43°C：选择三者时参考为58°C；只选择两块盘时参考为43°C。两路的选择互不影响，网页显示是哪一个来源触发。

两个阈值为整数，要求 `low_temp < high_temp`：

| 设置 | 行为 |
|---|---|
| 低温阈值 `low_temp` | `T < low_temp` 时静音；等于时进入普通 |
| 高温阈值 `high_temp` | `low_temp <= T <= high_temp` 时普通；`T > high_temp` 时全速 |

例如低温 55°C、高温 70°C：54.9°C 为静音，55°C 至 70°C 为普通，70.1°C 为全速。升温、降温、首次采样与运行中编辑均使用相同边界，不依赖上一档位；越线在下一轮有效采样切换，可以跳过中间档。独立 CPU 保护和所选设备临界温度保护优先于这两个用户阈值，因此仍可在普通温区触发安全全速。

阈值允许15–85°C。静音／普通输出可分别设置10–100%，普通不得低于静音，全速固定100%。固定输出接口同样允许10–100%整数，快捷高／中／低仍为100／75／50%。请求输出按0–255映射，10%四舍五入为raw26；策略、租约、监督进程与原生guard一致拒绝低于raw26或零输出。输出比例不是RPM比例，也没有实机证明与风速线性对应；最低可稳定转动的机械响应不能由请求值推断。

10%下限需要本版Python控制服务、监督进程与原生guard整套匹配，随同一个镜像和UI包更新。旧版本可能拒绝raw128以下的租约或转为安全全速，不能只改网页绕过底层范围。原有50–100%配置保持原值。过热、缺测、租约过期与故障恢复仍使用安全全速，不随用户最低输出降低。

CPU／sysfs 每秒采样；硬盘 SMART 不再后台采集，仅使用所有者显式刷新后的合法缓存，不能承诺持续温度采样。SMART 测量三十秒即过期，目录原九十秒上限不延长上游寿命；必要来源缺失仍按下文安全保护处理，不为风扇自动查询硬盘。网页保留实际采样时间，页面刷新不延长旧值。持续自动温控宜使用可持续采样的 CPU／主板来源；单次刷新合同见 [SMART 按需刷新](smart-refresh.md)。

## 保护与异常

所选必要来源丢失、无效或过期时，本路使用安全全速。0°C是合法数值，不当成缺测。明确且未过期的休眠盘可从温度比较中暂时排除；所有所选盘都休眠时使用静音输出，CPU保护仍保持。

即使本路只选硬盘，或使用固定输出，也持续检查全部可读CPU保护温度。CPU达到80°C或更低的已报告临界温度时全速；CPU保护温度不可读也全速。所选设备报告临界温度且越线时，同样覆盖自定义阈值。

监督服务独立于小屏的systemd控制组。控制进程死亡、短租约过期、身份变化或写入失败时，监督服务请求安全高档并恢复原厂执行者。恢复未确认会明确显示，不能只因自定义停止就显示恢复成功。实际故障处理不能替代风扇、接线和硬件检修。

## 原厂程序与恢复

原厂 `/histor/bin/temp_control` 的CPU线程每约10秒重写一次输出，不能简单靠更快写入抢占。它还负责硬盘休眠，因此不直接停掉整进程后弃用。

此版本只在用户应用自定义规则后，由独立监督服务重启一次同一原厂程序，加载RAM中的窄范围适配层。适配层仅处理 `/dev/hikio` 的CPU `0x5798`／系统 `0x5799`请求和被选通道；未选通道及磁盘相关请求透传。CPU单路、系统单路和两路均采用通道掩码区分。注入环境不会传播到执行其他程序的子进程。

原厂的硬盘休眠线程继续存在，但交接中的进程重启会重建它的计时状态。原厂二进制、启动脚本和内核模块不被替换，不重启 `emhistor`，不为自定义控制把原厂 `fan_mode` 持久改成高档。官方应用若更改系统风扇策略，Toolbox主动让回控制并报告冲突。

`emhistor` 仍可能在不改变策略值时直接写入风扇。监督服务先检查策略冲突，再以约1秒的有界周期重申自定义目标；这类外部写入可能造成一轮短暂变化。界面显示请求输出，不能将请求回执当作实际PWM或RPM读回。

网页将通道选为“自动”并保存即可恢复该路原厂管理，不再提供单独的“两路恢复原厂管理”按钮。退出接管先持久保存停用意图，再由监督服务恢复原厂进程和已有策略；系统选择其他原厂档位时再按前述事务切换。自动模式恢复前先保持安全高档，之后按原厂自己的采样周期调整；这不是精确还原不可读的旧PWM或RPM。

进程出现、执行文件匹配或保护模块已映射，都不能单独证明原厂程序已经启动完成。原厂策略同步会向 `temp_control` 发送 USR1／USR2 信号；因此接管和恢复都必须先确认相应信号处理器已安装，再同步策略，并在同步后持续核对同一进程身份仍存活且只有一个执行者。没有通过这些检查时不报告恢复成功。

### 接管就绪与短读修复

2026-10-28 的实机诊断确认：同一接管进程的信号处理器、身份和唯一执行者检查均通过，完整读取的 maps 为 7425 字节且 guard 路径精确匹配；旧接管检查只读到 4069 字节，未看到后面的映射，持续误判 `guard_ok=false` 并在 20 秒后恢复原厂。此前将问题归因于稳定窗口回退的判断不成立。

`/proc/PID/maps` 属于可能分段返回的内核文件，单次读取返回少于请求长度不能当成文件结束。原生适配层统一循环读取至 EOF，最多读取上限加一字节用于检测超限；仍保留普通文件、非阻塞与不跟随符号链接检查。超限或任意一轮读取错误均返回不可用，不拿部分内容通过身份或就绪检查。此修复不放宽 guard 匹配、唯一进程、信号处理器、150 毫秒稳定窗口或租约保护。

成功接管仍按既有顺序执行：保存原厂恢复信息，启动带通道掩码及短租约的 guard 进程，确认完整映射和信号处理器稳定就绪，安全同步原厂策略，核对身份和租约，再写入目标并发布 `phase=active`。只接管 CPU 时，系统风扇请求与硬盘休眠逻辑继续交给原厂；退出或租约失效时请求安全高档并恢复原厂程序。实机验收通过 `/api/dev/fan` 发起带采集的明确重试，必须同时观察 `guard_ok=true`、`phase=active`、对应通道 `active=true` 和后续写入回执；这些软件状态仍不等于实测 RPM。

恢复未确认时，保留 RAM 中权限为 `0600` 的原始恢复描述符，供受限恢复流程继续使用；它包含启动参数、环境与目录，不在网页或日志中展示。只有原厂进程及策略恢复均确认后，才清除其中的原始启动信息。

**旧版本出现 0 个 `temp_control` 进程时：**旧状态文件即使记录 `released`、`restore_ok=true`，也不能证明当前已恢复。如果旧流程已清除了恢复描述符中的原始启动信息，就不能安全重建原厂环境，也不要连续尝试保存。先部署包含本次修复的新镜像，再在保存业务后重启 NAS 一次，让原厂开机流程恢复温控进程；重新确认唯一原厂执行者和接口能力后，才由用户再次明确应用配置。规则数据卷可以保留。

## 支持范围与持久化

只有同时通过以下检查才开放实际接管：已加载hikio完整GNU note匹配支持版、温控二进制SHA256匹配已分析固件、唯一原厂进程身份、正确字符设备、原厂策略和同步接口，以及可加载的Linux amd64适配层。未知固件或驱动保持原厂控制，页面说明缺失条件，不提供绕过开关。

原厂的 `/tmp/nand_config/config.txt` 可以在 JSON 末尾保留 NUL 空字节。读取此已知文件时兼容尾部 NUL，但不改写文件；仍只接受整数 `fan_mode` 2／3／4／5，拒绝中间 NUL、坏 JSON、超出1 MiB或符号链接。此兼容不用于 Toolbox 的租约、恢复描述符和状态文件，它们继续严格校验。

保存（保存并应用）不可用时，页面优先显示具体预检条件，例如原厂策略配置无效、同步接口不可用或保护模块缺失。只有固定的预检原因可以显示；其他异常仍显示身份未验证，不导出原厂配置、进程环境或内部路径。修复配置读取的误判不代表跳过硬件身份检查，也不自动触发接管。

适配层由Debian Bookworm构建阶段编译，随经过哈希校验的UI包展开到 `/run`。Python规则服务、监督服务、租约、恢复描述符和适配层均不覆盖官方目录。具体ABI与静态证据见 [原厂接口分析](histor-interfaces.md)。

规则保存在独立Docker数据卷的 `fan-policy.json`。待用配置与最后成功应用配置分开保存；只有已经成功应用的规则才标记为下次启动恢复。单纯保存新规则不会偷偷替换仍在运行或重启后恢复的旧规则。故障导致自定义停止后，停用自动接管并提示检查；明确恢复原厂请求也会先保存停用意图。

容器重建和镜像更新复用原数据卷时规则保留。删除部署后重启，RAM适配与临时服务消失，官方显示和启动文件仍在；保留数据卷可以留住配置。已关闭的NAS本机网页与触屏不能执行开机。

软件验证使用模拟温度、假进程／假原生控制和Linux ioctl替身，覆盖两个阈值的等号边界、升降温一致性、最高温、缺测、旧版严格校验与迁移、待用／生效配置隔离、持久化、租约与恢复；这些不代表已经在用户NAS上验证机械风速、物理通道对应或所有固件运行状态。
