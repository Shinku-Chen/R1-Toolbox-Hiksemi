# 风扇实机软件验收（2026-10-28）

验收镜像为 `ghcr.io/shinku-chen/r1-toolbox:sha-db9ce08b599b1eb6cb90088a949c57c6b08dad35`，设备为 HikSemi R1，固件为 Build_260907。以下结果验证原厂档位、独立控制、监督回执和恢复流程；目标百分比及 raw 均为请求输出，不是实测 RPM。

## 方法与初始状态

操作前通过 `/api/dev/fan` 的 `snapshot` 核对完整预检、唯一原厂进程和信号处理器，10 项预检通过。两路实际均为原厂管理，系统原厂为低档（模式 2）；保存的 CPU 固定 100% 仅为待用草稿，`active_on_boot=false`。

每项操作前启动 `capture`，每次采集 60 秒、间隔 250 毫秒。独立接管和退出后的稳定状态至少观察 30 秒；同时保存 `/api/r1`，因为诊断策略摘要不包含全部原厂档位和待用配置字段。上一个任务完整保存后才启动下一个任务。

接管通过条件为：对应通道实际 `active=true`，当前监督目录 `phase=active`，当前唯一 `temp_control` 的身份、信号处理器、完整 maps 和 guard 精确匹配均通过；同一监督目录的 `applied_sequence` 连续增长。退出通过条件同时要求本次目录 `released`、`restore_ok=true`，以及当前唯一原厂进程存活、信号就绪、没有 guard。

温控使用真实的 coretemp 温度来源，阈值为 34／44／64°C，静音输出 55%、普通输出 75%。完整采样自然出现 45°C，观察到 quiet55%／raw140 升至 normal75%／raw191；温度随后回落到 38–43°C、仍高于静音阈值时保持普通档。没有通过压力或升温制造全速条件。

首轮名为 `systemauto` 的测试只设置 `mode=vendor`，验证的是退出系统接管并保留原厂低档；它不能替代显式设置 `vendor_mode=auto`。首轮 CPU 退出测试的起点已经释放，也不能独立证明从 active 退出。因此另行建立明确的 active 前置状态，单独补测两个退出组合。

部分首轮 60 秒采集中，30 秒稳定窗口之后还存在配置应用和正常释放请求，用户已确认是其手动切档。本文不将整个 60 秒窗口表述为同一 guard 持续稳定，也不把人工切换归为自动控制故障。结论分别依据明确的稳定窗口和补测切换证据。

## 恢复与证据

每轮收尾先退出独立接管并确认当前原厂进程恢复，再设置系统原厂低档，最后只保存原始待用草稿，不重新应用该草稿。首轮及退出补测的收尾均验证：两路 inactive、`busy=false`、恢复确认、`active_on_boot=false`、系统低档、原草稿逐字段一致，错误为空。

收尾后的独立复读又观察到用户的配置变化：保存配置已变为 CPU 原厂管理、系统原厂低档，`pending_changes=false`；硬件仍为两路原厂管理，无错误，完整预检及当前唯一无 guard 原厂进程均通过。因此只声明原草稿在收尾时已还原，不把它描述为最终仍未改变；最终保留用户最新选择，没有再次覆盖。

原始本地证据按原厂四档、手动各阶段及补测分目录保存，包含请求／响应、稳定快照、完整捕获结果与收尾状态。当前目录和 PID／启动时间用于关联本次操作，不使用历史 `released` 文件代替当前恢复证明。验收脚本的通过标记还经过原生子代理的独立证据复核。

## 边界

- 当前固件没有提供有效 RPM；声音、风量和逻辑通道与物理风扇的对应仍需现场确认。
- 温控尚未覆盖达到全速阈值、降至静音阈值、过热和温度缺测的实机分支。
- 本验收脚本 10 秒无 HTTP 请求不等于服务重启验收；本轮没有重启 NAS、重建容器或注入进程／租约故障。

控制原理和保护规则见 [独立风扇温控](fan-policy.md)，静态接口证据见 [原厂接口](histor-interfaces.md)。
