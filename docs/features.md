# 功能与支持条件

本项目面向海康 R1 官方固件。附件用于核对需求、协议和设备事实，前端与后端独立实现。**代码已接入**不等于**当前 NAS 已实机验证**；功能只有在检测到可信来源后才显示，控制还需要来源与操作范围明确。

## 核心功能矩阵

| 功能 | 本版范围 | 可用条件与限制 |

| 小屏信息层级 | 七个入口，点击进入二级/三级详情，始终可返回；左右手势切换主页面 | 面向 376×960，兼容 320px 宽；详情中不强行用滑动替代内容滚动 |
| 护眼显示 | 低饱和暗色、正文 20px/说明 18px、单列大指标、两行大导航，保留 80–140% 字号调整 | 320px 与 376px 下详情可滚动；可自行调低背光或启用夜间调暗 |

| GPU | DRM/sysfs 设备、可读利用率和显存 | 不保证 Intel 核显提供利用率；无数据的专属模块隐藏 |

| 原厂风扇转速 | 识别官方 /dev/hikio 与配套 product_test 的 cpu/sys 输出 | 当前 NAS 查询 rc=0，但 ioctl 报错且返回 cpu[-1]-sys[-1]；保留未知，不展示假 RPM |
| 通用风扇转速 | 所有可读 fanN_input，即使没有 PWM | 显示 driver/channel/RPM；0 RPM 与未知不同；不推断其物理位置 |
| 原厂系统风扇策略 | 按已加载模块完整 GNU note 白名单开放低/中/高/自动 | 本机 note 已匹配支持调速的 initrd 版；确认操作时再核验。未知/旧版只读，RPC 成功不代替物理效果验证 |
| 原厂 CPU 风扇策略 | 未接管或恢复原厂时，保留厂商每 10 秒自动温控 | 原厂 fan_mode 不控制 CPU；新的独立接管通过受监督适配层协调，不靠更快写入抢占 |
| CPU／系统独立温控 | 两路分别选原厂／温控／固定输出，多选来源取原始最高 °C | 网页双卡、小屏分别显示来源／温度／新鲜度／请求输出；逻辑通道与机械效果仍待实机验证，见 [独立温控](fan-policy.md) |
| 独立温控阈值与输出 | 每路 Ts<Tn<Tf，阈值 15–85°C；静音／普通 50–100%，全速 100% | 升温下一轮升档，全速降档低于 Tf−3°C，普通回静音到 Ts；最低 raw128，不停扇，百分比不是 RPM |
| 温控来源与时效 | CPU／主板 sysfs 每秒读取，3 秒有效；SMART 通常 30 秒采样，90 秒有效 | 磁盘身份与原采样时间保留；未确认身份、丢失或过期不可当有效来源；明确且新鲜的休眠盘不主动唤醒 |
| 独立保护与恢复 | 选源缺测／过期、CPU ≥80°C 或更低临界值时保护全速 | 即使手动或只选硬盘也检查 CPU；独立 systemd 监督租约与执行者，恢复未确认明确报错，不伪造 RPM |
| IT87 风扇独立通道 | 显式接管、手动 50–100% 占空比、低/中/高 60/80/100%、软件自动温控 | 当前官方固件未发现 IT87 hwmon/PWM；不自动加载模块，不走 /dev/port |
| IT87 自定义曲线 | 2–8 个温度/占空比点，温度 20–90℃递增，占空比 50–100% 非降 | 仅针对受支持 hwmon 通道；CPU 温度缺失或 ≥80℃请求满速；不等于官方策略、不在开机自动恢复 |
| IT87 故障回退 | 接管通道同号 RPM=0 请求满速并报告原因 | 同号 RPM/PWM 不代表已确认物理映射；回退不能替代硬件检修 |
| RGB 接口验证 | 明确选总线，读取 0x26 的身份 0x01=0x55、模式 0x90 和亮度 0x91 | 非强制、不扫描所有地址；写入前重验，失败撤销此前控制能力；当前灯效待实机确认 |
| RGB 颜色/灯效/独立亮度 | #RRGGBB，关闭/常亮/彩虹/呼吸，亮度 0–100% | 亮度独立写 0x91，原始值 round(255×百分比/100)，不缩放颜色分量；实际效果待实机确认 |
| 背光/息屏/唤醒 | 亮度 5–100%，立即息屏、首次触摸只唤醒 | 需要 backlight/blank；原始亮度 0 不能独立判断屏幕已关闭 |
| 轮播/页面选择 | 可选主页面，至少保留一页；0–3600 秒，0 关闭轮播 | 设置入口始终保留；详情阅读时不自动打断 |
| 空闲息屏/夜间亮度 | 0–86400 秒、支持跨零点 HH:MM、夜间亮度 5–100% | 夜间调暗不同于固定定时开关屏 |
| NAS 关机/重启 | 界面二次确认，5 秒可取消，固定 systemctl 操作 | 仅用户触发，不在部署或测试中执行真实电源动作 |
| Docker 列表/统计 | 状态、镜像、端口及可用资源统计 | 宿主 Docker 命令和权限可用 |
| Docker 启动/停止/重启 | 确认后执行，保护 Toolbox 自身 | 不提供创建、删除、exec、prune、镜像或 Compose 管理 |
| libvirt 虚拟机 | 列表/状态，确认后 start/shutdown/reboot/suspend/resume | 宿主实际有 virsh/libvirt；无 destroy/删除；缺失时隐藏 |
| 设置持久化 | settings.json 保存面板；fan-policy.json 分开保存风扇待用规则与最后成功应用规则 | 纯保存不接管、不替换运行或开机恢复规则；成功应用才启用恢复。image 部署缺可写卷会在接管小屏前失败；更新需复用原卷 |
| 网页配置 | IPv4 局域网 HTTP 默认 18732，一次性配对、独立会话、CSRF/同源保护 | 配对码只能由小屏主动生成，180 秒有效；会话启动内最多 8 小时；支持面板设置、两路独立风扇配置及已验证屏幕/灯光操作，不能执行任意命令 |

这里的“CPU 转速”指 **CPU 散热风扇 RPM**。CPU 自身提供的是频率 MHz/GHz，不能将频率与风扇转速混为一项。

## 官方风扇路径与验证边界

这台用户 NAS 的官方内核为 6.1.66-001。此前探测只有 acpitz/coretemp，没有 IT87 hwmon/PWM。gpio-it87 是 GPIO 驱动，不能代替风扇驱动。**这只能说明标准 PWM 路径不可用，不能据此断言官方没有风扇接口。**

本轮继续分析发现，官方体系中确有 /dev/hikio、product_test 读取入口，以及 subsystem 的 set_fan_status 系统风扇策略：模式 2/3/4/5 对应低/中/高/自动，模式 1 不提供。但存在协议不等于物理执行链有效。详细证据见 [官方接口审查](histor-interfaces.md)。

当前 NAS 的只读探测已确认 `/dev/hikio`、`/histor/bin/product_test`、`/var/tmp/emhistor` 与 `/tmp/fan` 存在。但 `product_test -o` 虽退出码为 0，内部两次 ioctl 均报错并返回 `cpu[-1]-sys[-1]`；这不是有效 RPM，更不能换成 0。此次 HTTP 7000 端口连接被拒绝，也不能把它当成可用 HTTP 后端。

进一步追踪同版固件：活跃 temp_control / emhistor 路径使用 0x5798/0x5799 调速。完整 rootfs 的 hikio 未实现，而 initrd 另有一份不同模块，确实实现这两个写请求与 0x5796/0x5797 温度读取。两版都缺旧 RPM 0x5793/0x5794，所以旧测速失败不能单独推出调速失败。用户随后读取实际加载模块的完整 GNU note，已与 initrd 支持版 c909da338be2c4700bb00b233cb189e7a32655b7 匹配；原厂 Unix GET 也已实测返回精确 b'5'，与 auto 配置一致；不能再按 rootfs 文件推断本机驱动不支持。详见 [识别证据](histor-interfaces.md)。

另对厂商 bin 中 16 个含相同 direct SuperIO 用户态函数的 ELF 独立复核：未发现外部直接 call/jmp 进入函数体或八字节函数指针引用，多个 daemon 出现该字符串可以由静态公共库链接解释。这不否定 initrd 驱动内部已经实现的内核 SuperIO 控制。其他机型的 ARM PWM 和 /proc/it86 分支不能直接套到本机。

2026-10-27 的静态结论仍成立：原厂 `fan_mode` 仅作用于 `0x5799` 系统风扇；CPU 线程每 10 秒写 `0x5798`，原厂 API 没有关闭该 CPU 线程的独立开关。该限制只针对直接使用原厂策略，不代表新版本仍不提供 CPU 配置。

2026-10-28 的独立接管另走受监督的 RAM 适配层：白名单驱动、温控二进制 SHA256、唯一原厂进程、字符设备和编译适配层全部通过后，用户确认应用才重启同一 `temp_control`，仅处理被选 CPU／系统请求。硬盘休眠线程继续运行，重启会重建其计时；未选通道及磁盘请求透传。不会修改原厂二进制、持久改写 `fan_mode` 或重启 `emhistor`。原厂系统档位与其他 PWM 入口在独立控制运行、切换或恢复未确认时不混用。详细流程见 [独立风扇温控](fan-policy.md)。

原厂策略适配器仍按实际已加载模块的完整 GNU note 白名单决定写入能力，未知、缺失或 rootfs 旧版只读；其普通后台探测不发送有副作用的原厂 GET/SET/信号。独立接管和恢复则在已授权流程中同步既有原厂策略，不写入替代 `fan_mode`。支持接口和成功回执均不能证明本机机械调速已经观察成功。

原厂协议会持久保存风扇配置，并发信号或请求底层执行，上层还可能忽略底层结果。因此回执和策略读回不是转速验证。用户明确选择原厂系统风扇策略后，停止 Toolbox、恢复官方 UI 或重启不应理解为撤销该策略；这与临时 hwmon 接管后恢复原 PWM 不同。

附件对 fan2/fan3 和 pwm2/pwm3 的 CPU/机箱角色存在相互矛盾的注释。通用通道保留原始名称；官方 cpu/sys 字段也要以本机协议和读数核验为准。不能仅凭编号断言哪个物理风扇受控。

## 数据、控制与恢复

UI 和 Python 服务从经校验的 /run/r1-toolbox RAM 包运行，前端只读绑定到官方 Electron 的私有文件视图。官方 AppImage、解包版 dist、启动脚本保持原样；Docker 部署容器完成后停止，宿主临时小屏服务继续运行。

独立命名卷保存面板 `settings.json` 和风扇 `fan-policy.json`。风扇待用配置与最后成功应用配置分开保存；纯保存不会改变实际控制，也不会替换下次启动恢复的旧规则。明确恢复原厂或故障停止接管时停用自动恢复。image 模式没有可写卷会拒绝接管，不静默退回内存设置。采样历史、IT87 接管／曲线、RGB 验证和待执行电源请求仍不作为开机配置保存。

本机读取接口为 `GET /api/status`、`GET /api/toolbox`、`GET /api/insights`、`GET /api/fan-policy`。本机 `POST /api/action` 需要当次启动的 `X-R1-Token` 和 Host/Origin 校验；令牌仅传给小屏 Electron，普通文件预览只读。`GET /api/web-config` 只返回服务状态和地址，不返回配对码；小屏主动生成的一次性码用于 IPv4 局域网网页的独立 HttpOnly/SameSite 会话，后续写入还需 CSRF 和同源校验，网页不复用小屏令牌。

独立温控的保存、应用和两路恢复经白名单 `fan.policy.*` 操作完成。保存不需要硬件可用；应用／恢复须明确确认并等待异步状态，不能因请求 `ok` 就当硬件生效。CPU/sysfs 来源每秒刷新、最多 3 秒旧读数；SMART 通常约 30 秒采样、最多 90 秒，网页刷新不会延长旧值寿命。RGB 仍是即时操作，不保存为开机执行配置。

正常停止宿主小屏服务时取消待执行电源请求，尽力恢复 hwmon、背光/blank；独立风扇监督服务在另一个 systemd 控制组继续处理控制进程退出、5 秒租约失效与原厂恢复。它先请求安全高档，再恢复原厂执行者及既有策略；恢复未确认必须保留错误并可重试。RGB 不自动恢复；用户另行确认保存的原厂系统风扇策略不自动撤销。断电、设备失效等情况仍不能保证恢复成功。

部署、更新与恢复官方界面见 [部署说明](../tools/boot-once/README.md)。
